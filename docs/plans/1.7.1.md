## How 1.7.0 works inside (new in this release)

- **Recipient-locale text.** `src/Engine/RecipientLocale.php` wraps every hook that stores or sends human text (toasts, bell rows, emails, activity posts) so it is built in the recipient's locale (`user()`), or the site locale for text everyone reads (`site()`). Never call `__()` before `init`: WordPress 6.7+ logs an early-textdomain notice (`DbUpgrader` and `Installer::maybe_install()` run at `plugins_loaded`; the translated seeds are deferred to init, see `tests/Unit/Engine/EarlyTranslationTest.php`).
- **Toast delivery is ack-on-display.** Readers (footer seed, heartbeat, REST poll, SSE) do not advance the member's cursor. Each payload carries `_id` and `_ack`; `assets/js/toast.js` sends `POST /wb-gamification/v1/members/me/toasts/ack` with the highest id H such that every received row with id <= H has actually appeared on screen. A held summary (behind a level-up card) pins the ack below itself. A client-only sessionStorage record (`wbgam-shown:<userId>`, at most 100 ids) stops the level-up card repeating after a reload. The server checks the id is one of the caller's own queue rows and only moves the cursor forward. No server-side key was added.
- **Owner colours.** `CSS::card_tokens()` in `src/Blocks/CSS.php` derives text, muted text, borders, medals, status inks, the focus ring, the badge plate and the field border from the owner's card background (WCAG luminance), independent of the theme's scheme. `src/shared/design-tokens.css` holds the shared rules: one focus ring (2px outline, offset, halo), card-text links, the accent button pair and form controls. They are `!important` with higher specificity on purpose: BuddyX 5.1.3 forces `:focus-visible { outline: 2px solid #2271b1 !important }`, button backgrounds at `button[type=submit]`, and form-field colours.
- **Translations.** Strings are in `languages/` (.pot, five .po, .mo, .l10n.php) and script translation `.json` files. WordPress finds a script's JSON by the md5 of the script's plugin-relative registered path, so they must be keyed to `build/Blocks/*/index.js` and `assets/js/*.js`, not to `src/`. After any .po or JS change run `bash bin/build-i18n-json.sh`. Regenerate in this order: `npm run build && npm run build:pot`, `msgmerge -q -N -U --backup=none` each .po onto the .pot, translate the new msgids, `wp i18n make-mo languages && wp i18n make-php languages`, `bash bin/build-i18n-json.sh`.

## Gates

`composer ci:no-journeys` (`bin/local-ci.sh`) runs lint, WPCS, PHPStan, PHPUnit and JS tests, coding rules, UX audit, enum and CSS contracts, Plugin Check (0 unbaselined errors; baseline in `audit/plugin-check-warning-baseline.txt`), boot and badge and clock contracts, motion tokens, `bin/check-i18n.sh` (fails on a string missing from the .pot or a .po, a broken placeholder, a stale .mo, .json or .l10n.php; only warns below 95% translated, `I18N_ENFORCE_COVERAGE=1` makes that fail) and `bin/check-no-emdash.sh`. `bin/test-check-i18n.sh` and `bin/test-check-no-emdash.sh` prove those two gates can fail.

Plugin Check and the release build need the plugin to sit inside a WordPress install (the scripts locate it from the plugin path). Run them from a checkout inside a Local site's `wp-content/plugins/`, not from `~/code`.

## Release flow (what was done for 1.7.0)

1. Work on a release branch from main; fix, test, commit (no attribution lines).
2. Scale gate: seed 10,000 members, benchmark, tear down (`wp wb-gamification scale seed --users=10000 --events-per-user=10`, `scale benchmark`, `scale teardown`); it writes `audit/.last-scale-pass.json`. Use an isolated site, never a shared one.
3. Smoke gate: the walker (`docs/qa/AGENT_SMOKE_RUNBOOK.md`) writes `docs/qa/.last-smoke-pass.json`; it must name the release version, have no `from` failure and no `from` debug.log issue, have sections A and B walked, and be newer than the HEAD commit. Any commit after the walk makes it stale, so freeze HEAD first.
4. `bash bin/build-release.sh` builds `dist/wb-gamification-<version>.zip` after all gates.
5. QA verifies that exact zip (sha256). Only after QA clears it and the owner says yes: push the branch, open the PR into main, merge when the required checks pass, delete and recreate the annotated tag on the merge commit, create a draft release with the zip named `wb-gamification-<version>.zip`, sign it (`~/.claude/skills/wp-plugin-release/scripts/sign-release.sh vapvarun/wb-gamification v<version> wordpress-gamification-plugin <zip>`), publish with `--latest`, verify the tag, asset digest and signature, then post one reply in the existing Slack thread (no broadcast, no mention).

Playground has no points tables until the plugin installer has run.
- **Themes for the matrix:** Reign 8.1.2, Twenty Twenty-Five, BuddyX 5.1.3, BuddyX Pro 5.1.4 (BuddyX dark: `localStorage['bx-color-mode']='dark'`). No newer BuddyX was available.
- **Keyboard checks** use a real Tab key and read `document.activeElement`'s computed outline and box-shadow after every press; `focus({focusVisible:true})` is only a shortcut.
